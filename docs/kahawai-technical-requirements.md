# Kahawai — Technical Requirements Document

**Version:** 0.1 (draft)
**Status:** For review
**Scope:** Backend (hub, mediahost, transcoder), its client-facing and inter-module contracts, and the hub's bundled web interface (admin UI + MVP web player, §6.5). Native client applications remain out of scope except where their needs constrain the backend.

---

## 1. Overview

Kahawai — Hawaiian for *stream*; also the Māori name of a New Zealand fish, from *kaha* (strong) + *wai* (water) — is a self-hosted media streaming platform for personal backups of series, movies, music, and anime. Users rip or back up media they own, place it on storage they control, and stream it to their own devices. The backend is written in Rust and uses GStreamer for all media handling: metadata and stream inspection, capability negotiation, and transcoding.

The system ships in two deployment shapes built from the same codebase:

1. **All-in-one binary** — a single executable that embeds the hub, one mediahost, and, by default, one full transcoder, suitable for a NAS or a single home server. The local transcoder may be disabled when video encode work belongs on external satellites.
2. **Modular deployment** — the hub, one or more mediahosts, and zero or more transcoders run as separate processes, potentially on separate machines, connected over the network. The hub itself performs direct delivery, remuxing, and audio-only transcoding; it is not a video transcoder.

The functional behavior visible to clients must be identical in both shapes.

## 2. Goals and non-goals

**Goals.** Reliable local-first streaming of personal media; correct handling of heterogeneous rips (varied containers, codecs, subtitle formats); direct play whenever the client can handle the source; transcoding only on capability mismatch; horizontal distribution of storage (mediahosts) and compute (transcoders); metadata enrichment from public databases; a stable, versioned client API.

**Non-goals (v1).** Acquiring media (no downloaders/indexers — subtitle acquisition per HUB-21..24 is the sole, deliberate exception); DRM; live TV/DVR; multi-tenant SaaS operation; federation between independent hubs; editing or re-muxing source files on disk (sources are treated as read-only).

## 3. Terminology

**Collection** — a unit announced by a mediahost: a media type (`series`, `movies`, `music`, or `anime`) plus a set of files with their on-disk metadata (paths, sizes, mtimes, and GStreamer-extracted stream info). `anime` is a first-class type spanning both episodic content and films, because its naming conventions, metadata ecosystem, and subtitle handling differ enough from western series/movies to warrant a dedicated pipeline (§6.6).
**Library** — a hub-side construct combining one or more collections of the same media type into a single browsable entity presented to clients.
**Item** — a logical media entity in a library: a movie, an episode, a track.
**Media source** — a concrete file backing an item. An item may have multiple sources (e.g., 4K and 1080p copies of the same movie, possibly on different mediahosts).
**Capability profile** — a structured description of what a client can play: containers, video/audio codecs with profiles and levels, max resolution/bitrate/framerate, subtitle formats, HDR support, streaming protocols.
**Play session** — the hub-managed lifecycle of one playback: negotiation, source selection, delivery (direct or transcoded), progress reporting, teardown.

## 4. Architecture requirements

### 4.1 Modules

**AR-1** The system shall consist of three modules: **hub**, **mediahost**, and **transcoder**, plus a shared core library.
**AR-2** The hub shall be the only module clients communicate with. Mediahosts and transcoders shall never be directly addressable by clients; all media bytes reaching a client are proxied or brokered by the hub (see AR-8 for the delegated-delivery exception).
**AR-3** Mediahosts and transcoders shall initiate connections *to* the hub (outbound registration), so they can live behind NAT or firewalls without inbound port forwarding.
**AR-4** A hub shall support multiple simultaneously connected mediahosts and transcoders. A mediahost shall be able to announce multiple collections.
**AR-5** The all-in-one binary shall run the hub, mediahost and a full transcoder in one process by default, replacing the network transport between them with an in-process transport, with no change in module logic. A deployment may structurally disable the in-process transcoder while retaining the hub's lightweight media work (remuxing and audio-only transcoding while video is copied) and accepting external transcoder satellites; this choice shall be durable configuration applied before video-encoder dry-runs, background video benchmarking or playback placement, not an admin drain toggle. The `hub` module alone always retains that lightweight work and never becomes eligible for video encode, tone-map, scaling, deinterlacing or subtitle burn-in merely because the full binary contains their implementation.
**AR-6** Modules shall tolerate disconnects: a mediahost dropping shall mark its collections unavailable (not deleted); a transcoder dropping shall fail over active sessions to another transcoder where possible, otherwise terminate those sessions with a client-visible error.
**AR-7** All inter-module protocol messages shall be versioned; a hub shall reject or degrade gracefully when a module speaks an incompatible protocol version.
**AR-8** *(Optional, v1.x)* The hub may issue signed, expiring delegation tokens allowing a client to fetch stream bytes directly from a mediahost or transcoder when network topology permits, to take the hub out of the data path. This must be opt-in per deployment.

### 4.2 Data flow

**AR-9** Control plane (browse, search, negotiate, session management) always flows client ↔ hub.
**AR-10** For direct play, media bytes flow mediahost → hub → client with byte-range support end to end. Lightweight stream preparation is performed by the hub itself in this same path: remuxing (repackaging supported streams into a supported container, no re-encoding), and audio-only transcoding or downmix while every video stream is copied. Those sessions shall never require or engage a transcoder and shall be fully functional in deployments with zero transcoders attached. Any session that encodes video—including tone-mapping, scaling, deinterlacing or subtitle burn-in—requires a full transcoder, either external or the enabled in-process transcoder of all-in-one mode.
**AR-11** For transcoded play, the transcoder pulls source bytes from the owning mediahost via the hub's brokered channel (or directly, in all-in-one), produces segmented output, and the hub serves those segments to the client.
**AR-12** The control plane and the bulk-media byte plane shall be isolated such that data-plane backpressure can never stall control traffic: a lease or segment stream that stalls (slow client, paused pipeline) must not delay heartbeats, session commands, or registry messages. Concretely, they must not share a transport connection or any connection-level flow-control window.
**AR-13** **Capability is a first-class, cross-module contract.** Every participant declares what it can actually do — clients their decode/render profile (HUB-14), transcoders their encode/decode/filter inventory (TC-1), mediahosts nothing (MH-12 withdrawn 2026-08-02 as a false premise — see its amendment; nothing a mediahost could declare decides anything the hub should act on), the hub's lightweight in-process worker for audio-only encode, and a full in-process transcoder only in all-in-one mode — and every decision that could fail on a peer's limits is made from those declarations rather than from assumption. Four rules govern what may be declared:
1. **Measured, not assumed.** A declaration is the result of probing the running system — a dry run of the element, a feature test in the browser, a timed sample — never a version number, a config value, or a compiled-in constant. A capability that cannot fail to be true is not one.
2. **A capability decides something, or it is a protocol version.** If every peer necessarily answers the same way, the answer belongs in the AR-7 handshake, where an incompatible peer is refused once and loudly, and not in a capability field that must be carried, stored and reasoned about forever.
3. **Declared in the terms the decision needs.** Where the decision is *whether the work will keep up*, the declaration is a **rate**, not a boolean: "can" and "can at the speed this needs" are different questions, and a box that performs a filter at half of realtime answers yes to the first and no to the second. Where the decision is *whether an operation is affordable at all*, the declaration states the cost class (local disk versus a brokered byte plane differ by orders of magnitude for the same read pattern).
4. **Absence degrades honestly.** A missing capability changes the plan before the work starts, and the session verdict states what was actually done — never what was intended. Promising a tier that then silently does nothing is a defect, not a degradation.
Capabilities shall additionally be **falsifiable from the other side**: any declaration a client makes must be maskable for testing (HUB-14), so every negotiation branch is reachable without hunting for a peer that genuinely lacks the feature.

### 4.3 Trust and enrollment

The hub is the certificate authority for its deployment. Mediahosts and transcoders (collectively "satellites") are admitted through a one-time, admin-confirmed certificate enrollment and thereafter authenticate with mutual TLS.

**SEC-1** The hub shall operate an internal CA: it generates a CA keypair and self-signed CA certificate on first start and stores the private key locally with restrictive permissions. The CA private key shall never leave the hub.
**SEC-2** A satellite without a certificate shall, on first start, generate a keypair locally (the private key never leaves the satellite), build a CSR identifying its module type and name, submit the CSR to the hub's enrollment endpoint, and print a short verification code to its console. The code shall be derived from a cryptographic fingerprint of the CSR so that it commits to the satellite's public key.
**SEC-3** The hub shall hold submitted CSRs as pending enrollments and shall not sign any of them automatically. An administrator approves an enrollment by entering the satellite's console code on the hub (CLI or admin UI); the hub shall verify the entered code against the pending CSR's fingerprint and reject on mismatch. Pending enrollments shall expire after a configurable timeout, and enrollment submissions shall be rate-limited and logged.
**SEC-4** On approval, the hub shall sign the CSR and return to the satellite: its signed certificate and the hub's CA certificate. The satellite shall persist both and shall pin the CA certificate for all future connections.
**SEC-5** All subsequent inter-module connections (control plane and byte plane) shall use mutual TLS with **allow-list admission**: the hub accepts a connection only if the satellite presents a certificate that chains to the hub CA *and* whose fingerprint is present on the hub's allowlist of enrolled satellites — chain validity alone is never sufficient. Unknown fingerprints are refused (fail closed), so even a certificate validly signed by the CA grants nothing unless it is the currently registered certificate of an enrolled satellite. The satellite accepts a connection only if the hub's certificate validates against the pinned CA, so satellites can positively identify the hub.
**SEC-6** Removal from the allowlist shall be coupled to satellite deletion: a satellite's fingerprint is removed if and only if the administrator deletes the satellite from the hub. Deletion removes the fingerprint, immediately terminates the satellite's active connections and sessions, and refuses reconnection at the TLS layer. Deleting a mediahost additionally deletes its collections (cascade per HUB-20); deleting a transcoder removes it from the scheduler. A deleted machine can only be re-admitted through a fresh enrollment (SEC-2). Transient disconnects remain governed by AR-6 and never trigger allowlist removal or data removal.
**SEC-7** Satellite certificates shall have bounded validity and be renewed automatically before expiry over the existing mutually authenticated channel, without a new console code. Renewal shall update the allowlist atomically with certificate issuance — the new fingerprint is registered before the new certificate is returned, and the old fingerprint is retired only once the satellite reconnects with the new certificate. If a bounded grace period elapses without that reconnect, it is the unused *new* fingerprint that is retired and the renewal is treated as failed and retried later; the certificate in active use is never invalidated by its own renewal, so a satellite cannot be locked out.

## 5. Mediahost requirements

**MH-1** A mediahost shall be configured with one or more collections, each defined by a media type and one or more root directories.
**MH-2** On startup and on demand, a mediahost shall scan its roots — on-demand scans are scoped to a single collection, never "everything" — and it shall watch them for changes (filesystem notification where available, with periodic rescan as fallback) and push incremental updates to the hub.
**MH-3** For every media file, the mediahost shall extract technical metadata using GStreamer's discovery facilities: container format; per-stream codec, profile/level, coded resolution, pixel aspect ratio, normalized display orientation and resulting display dimensions, framerate, pixel format, bit depth, HDR metadata (HDR10/HLG/Dolby Vision presence), audio channel layout and sample rate, embedded subtitle streams and their formats, chapters, duration, and container-level tags (including music tags: artist, album, track number, disc number, embedded art). Rows predating PAR/orientation support shall be filled by a targeted exact-source mediahost worklist; this shall not trigger a scan or reconciliation, alter scan generations, or infer the facts from old `streams_json`. Probe results and terminal failures belong to the stable physical source and are replaced when that source revision changes.
**MH-4** The mediahost shall detect external companion files: sidecar subtitles (`.srt`, `.ass`, `.sub/.idx`, `.vtt`), external audio, local artwork (`poster.jpg`, `cover.jpg`, `folder.jpg`), and NFO files, and associate them with the correct media file. It shall additionally enumerate MKV attachments — declaring font attachments (TTF/OTF) with their identity and location in the file record — but shall not extract attachment payloads at scan time; they are retrieved on demand per HUB-32/HUB-34.
**MH-5** The mediahost shall compute a stable content identity per file (path + size + mtime fast path; content hash of head/tail segments for move/rename detection) so the hub can preserve item identity and watch state across renames and moves. For video files it shall additionally compute the OpenSubtitles moviehash (file size + 64-bit sum of the first and last 64 KiB) in the same read pass and include it in the file record for subtitle matching (HUB-22).
**MH-6** The mediahost shall serve byte-range read requests for its files to authorized peers (hub, brokered transcoder) and shall never expose write operations on media files.
**MH-7** Scanning shall be rate-limited and resumable so that a scan of a large library (100k+ files) does not saturate disk I/O and survives restarts without starting over.
**MH-8** Unreadable or corrupt files shall be reported to the hub with a diagnostic rather than silently skipped.
**MH-9** For collections where the hub requests it (anime exact matching, HUB-30), the mediahost shall compute full-file ED2K hashes as a low-priority background job separate from the scan (full-file reads are expensive) and report them incrementally via a dedicated hash-report message. The mediahost keeps no hash state of its own: the hub persists hashes on the file record, and content-identity copy-forward (MH-5) carries a hash across renames, moves, and rescans — giving at-most-once hashing per content identity with no additional persistence. If the filename carries a CRC32 tag, the mediahost may verify it during the same pass and report mismatches as integrity warnings.
**MH-10** Each collection shall carry a monotonically advancing **sync generation**, persisted by the mediahost and advanced when a change batch is committed to and acknowledged by the hub. On reconnect, generations are compared per collection: a match means the hub's picture is current — no file manifest is exchanged and no directory walk is triggered; availability simply flips on. On mismatch, reconciliation is incremental: un-acknowledged changes are replayed and a files-seen enumeration lets the hub prune records for files that vanished while disconnected. Together with content identity (MH-5), this is the incremental synchronization mechanism; reconnection alone shall never require a rescan (NFR-3, acceptance criterion 4).
**MH-11** Auxiliary mediahost work shall run in a three-tier priority runner: (1) urgent subtitle/attachment extraction (HUB-34 ladder step 3 — a viewer is waiting; never idle-gated, preempts lower tiers), (2) ED2K hashing (MH-9, idle-gated), (3) background subtitle pre-warm (idle-gated, strictly below hashing). *Idle* is defined as: no scan in progress **and** no read lease currently being served.
**MH-12** ~~A mediahost shall declare what its access to a collection permits, so the hub stops discovering it by failure (AR-13). At minimum: which extraction operations it can perform (text subtitles, image display sets, attachment declaration), and that index-driven reads are affordable *there*.~~ **WITHDRAWN — false premise (owner, 2026-08-02).** Built and reverted the same night; what the build measured is what disproved it.

The requirement assumed a mediahost's access varies in a way the hub must know about and route around. It does not, in either half.

*Nothing to declare.* The three index-driven extractions (text subtitles, image display sets, attachment declaration) are pure Rust in a crate with no cargo features, so every peer in every build answers the same — which AR-13 rule 2 already calls a protocol version, not a capability.

*Nothing to decide.* The remaining half was cost, and the measurement landed on the wrong noun. Probing one live host read **30 s for `movies` and 23 ms for `anime` — same disk, same mount, same host**: the variance is per-FILE container index quality (cue-addressed versus hopping every cluster header), not per-host access. A per-host, per-collection declaration cannot describe that, and per-file "will this one work" is answered by asking for that file, as it always was.

*And there is nothing to route around anyway.* A host too slow to walk its own index is too slow to serve the video, so it fails at playback, where the failure is. A deployment in that state wants fixing, not working around: **there are no sensible caps or refusals** (owner). The cap this requirement implies buys ~20 s of dead session start in a case that should not exist, and pays with silent wrong refusals — a tier withdrawn from a host that could have served it leaves no trace anywhere, while offering one it cannot costs a timeout and an honest re-plan. The asymmetry runs entirely against capping.

What survives, in AR-13 and unchanged by this: the byte plane's ~4 KB/s figure is real for **index-driven** reads — thousands of scattered small reads, round-trip bound — which is why an index walk is requested of the host that owns the disk and `extract_image_track` has no hub-side caller. It does not transfer to sequential whole-container reads, which are the throughput-bound direct-play pattern (AR-10) and are a legitimate hub-side fallback: the mediahost is the only source, so refusing that lease converts "slow" into "never".

## 6. Hub requirements

### 6.1 Registry, libraries, and identity

**HUB-1** The hub shall maintain a registry of connected mediahosts, their collections, and connected transcoders with their capability reports.
**HUB-2** Administrators shall be able to compose libraries from any set of same-typed collections, including collections from different mediahosts, and set per-library settings (name, artwork, preferred metadata language, enrichment providers, user visibility).
**HUB-3** Every item shall belong to exactly one collection, and alternate-source deduplication shall be restricted to that collection: sources in one collection that resolve to the same movie, episode, track or release become one item with quality-ranked sources selected at play time. Libraries only compose collections; attaching one collection to several libraries exposes the same item IDs and watch state in each. Items in different collections shall remain independent even when title, year or provider IDs match: no shared item identity, provider/manual/query state or watch state across collections.
**HUB-4** The hub shall parse file and directory names into candidate identities (title, year, season/episode numbering including multi-episode files and specials, absolute numbering for anime, artist/album/track for music) as input to enrichment, with per-item manual override.
**HUB-20** Deleting a mediahost (SEC-6) shall cascade: its collections are removed from all libraries, and the items/sources owned by those collections are removed from browse. Watch state and manual metadata bindings for affected collection items shall be archived keyed to content identity (MH-5) so that if the same media returns later in that collection namespace — via re-enrollment or import — item identity, manual matches and per-user watch state are restored. This is distinct from a disconnect, which only marks collections unavailable (AR-6).

### 6.2 Metadata enrichment

**HUB-5** The hub shall enrich items via pluggable providers behind a common trait, composed into per-media-type chains with **first-claim-wins** semantics: the earliest provider in the chain to supply a given field owns it. The normative default chains are — anime → [anime-native (AniDB/AniList, §6.6), TMDB, TheTVDB]; movies and series → [TMDB, TheTVDB]; music → [embedded tags evaluated at resolution time, MusicBrainz (plus Cover Art Archive)]. Anime episode and artwork data deliberately bridges to TVDB/TMDB through mapped IDs (HUB-31) rather than by independent matching. Chains are configurable **per media type** — amended 2026-07-26 from "per library": an item can belong to several libraries, so per-library precedence has no single answer to "who owns this field", while media type is fixed by the collection an item lives in. The order is editable at runtime and applies retroactively, which is affordable because every provider's answer is stored (§4.3). The provider set is extensible without touching core code.
**HUB-5a** Each enrichment pass shall be gated on the providers ITS chain declares, not on another pass's. A media type whose chain is fully configured shall enrich regardless of any other type's credentials.

**AR-13a** A dry run shall reproduce the chain a session builds, terminating in the element whose acceptance is being claimed. A probe that ends in a sink accepting anything measures only that the segment ran, and a capability verified that way can be false in every session — measured 2026-08-02: a box reported `tonemap: true` at 1.30x while every HDR session on it died at negotiation, because the probe ended in `fakesink` and named no encoder, so the segment's output pin fell back to a format list the real encoder could not take. Probes shall also be fed the input a real session produces (10-bit for the HDR path), since the narrowest negotiation and the largest cost both sit there.

**HUB-6** Enrichment shall fetch descriptive metadata (titles, plots, cast, genres, ratings, air/release dates, artwork, season/episode structure, album/release structure) and store it locally; the system shall remain fully browsable and playable when providers are unreachable.
**HUB-7** Provider access shall respect per-provider rate limits, cache responses with TTLs, support API keys supplied by the administrator, and support scheduled refresh of mutable metadata (e.g., ongoing series).
**HUB-8** Ambiguous matches shall be flagged for manual resolution rather than guessed above a confidence threshold; manual matches shall be sticky across rescans (keyed to content identity from MH-5).
**HUB-9** Local metadata (NFO, local artwork, embedded tags) shall be usable as an authoritative provider. **Amended 2026-07-26** from "inserts at the front of the applicable chain, overridable to a different position per library": `local` is not a chain member and holds no rank. It is asked before the chain and its answers sort ahead of every provider's. Ranking it would imply there is a sensible order in which a search result beats the file on the owner's own disk, and would leave a knob with one correct setting. The only thing that displaces it is the owner contradicting it — a manual pin elsewhere, or a rejection of the record its `.nfo` claimed — and then it steps aside wholesale, cover included, since overriding what the file says about a work is not a statement about one field of it.

#### Subtitle acquisition

**HUB-21** The hub shall support downloading subtitles from external subtitle services behind a pluggable provider trait, with OpenSubtitles (REST API) as the first implementation. The feature shall work out of the box with no configuration: the application ships with its own registered OpenSubtitles application API key, under which anonymous use is entitled to 5 API requests per second and 5 downloads per 24 hours. Administrators may optionally attach an OpenSubtitles user account to raise the download entitlement, may override the embedded application key with their own, and may disable the feature entirely. The anonymous download entitlement is consumed per deployment (it is not per user), which the interface shall make clear wherever quota is shown.
**HUB-22** Subtitle matching shall prefer exact file identification via the provider's file hash (for OpenSubtitles: the moviehash, computed by the mediahost during scan and carried in the file record) and fall back to metadata search (external IDs from enrichment, then title/year/season/episode). Preferred subtitle languages shall be configurable per user and per library and act as the default search filter.
**HUB-23** Downloaded subtitles shall be stored exclusively on the hub, in its own data store — never written to a mediahost or next to the media files (mediahost roots are read-only per MH-6) — versioned per item source and language, and registered as additional external subtitle streams so they participate in capability negotiation exactly like sidecar files (pass-through, format conversion, or burn-in per HUB-15). A downloaded subtitle attaches to the item source, not to the requesting user: it is automatically available to every user with access to that item, with the initiating user recorded for auditability.
**HUB-24** Subtitle downloads shall always be user-initiated: a user searches candidates for an item (filtered by their language preferences by default), sees language/release/rating/uploader and whether the match is hash-exact, and explicitly picks one to download. The hub shall never download subtitles automatically — not on import, not on a schedule, and not as a side effect of playback. The hub shall respect the provider's request rate limit and download entitlement, surface the remaining downloads and reset time to the user before and after each download — noting that the entitlement is shared across the deployment when running anonymously (HUB-21) — cache search results, retain uploader attribution with each stored subtitle, and allow users to delete or replace a mismatched subtitle. An exhausted entitlement shall fail the download with the reset time rather than queueing background work.

### 6.3 Users, auth, and API

**HUB-10** The hub shall support multiple user accounts with per-library access grants, per-user watch state (played/unplayed, resume positions, play counts), and an admin role for configuration.
**HUB-11** The client API shall be a versioned HTTP/JSON API plus a real-time channel (WebSocket or SSE) for session events and library-change notifications, with token-based auth (short-lived access tokens, revocable refresh tokens) and optional reverse-proxy/OIDC-friendly operation.
**HUB-12** The API shall expose browse (hierarchical: library → show → season → episode; artist → album → track), search across libraries, item detail with full technical stream info, image serving with server-side resizing and caching, playback endpoints, and admin endpoints (module registry, library composition, enrichment control, session monitoring).
**HUB-13** All state owned by the hub (registry, libraries, items, users, watch state, enrichment cache index) shall persist in an embedded database requiring no external services by default.

### 6.4 Playback and capability negotiation

**HUB-14** A play request shall include the client's capability profile. The hub shall compare it against each candidate source's streams and decide, per elementary stream, one of: **direct play** (container and all selected streams supported → byte-range serve), **remux** (streams supported, container not → the hub repackages without re-encoding, using its own GStreamer pipeline and no transcoder, per AR-10), or **transcode** (re-encode only the mismatching stream(s)). Audio-only transcode with video copied runs in the hub under AR-10; any video transcode is dispatched to a full transcoder.
**HUB-15** Negotiation shall account for: container support; video codec/profile/level; resolution, framerate and bitrate ceilings; HDR capability with tone-mapping fallback to SDR (per HUB-15a); audio codec and channel-count downmix; subtitle handling (pass-through of text formats the client supports, conversion between text formats, server-side decode of image-based subtitles to streamed bitmap display sets for clients that can composite them per HUB-32b, OCR-derived text tracks per HUB-32c, burn-in only as the last resort); and an explicit client- or user-imposed bandwidth cap.
**HUB-15a** When a source is HDR (HDR10/HLG) and the client's capability profile lacks HDR support, the hub shall tone-map the video to SDR during the encode, through a preference-ordered element chain whose per-box availability is reported via TC-1 and surfaced by the doctor. Acceptable output quality shall be verified against a test matrix of real HDR10/HLG sources before the tier is considered delivered. When no capable element is present on any eligible box, delivery falls back to the unmapped source with the session verdict stating so — never a silent failure and never a refusal to play.
**HUB-15b** Negotiation shall support **multiple encode targets**, chosen per session as the cheapest codec the client's profile accepts and the executor of that work verifiably encodes (preference by ubiquity: h264 → hevc → av1; audio aac → opus). For video encode, both video and accompanying audio targets come from the selected full transcoder. For audio-only encode with video copied, audio targets come from the hub's lightweight worker. Today's single hard-coded h264/aac target means a client that lacks h264 is refused even on fleets whose hardware encodes HEVC and AV1 natively (measured: the dev box's NVENC does both, VideoToolbox does HEVC). The enabling dependency is the segment container: MPEG-TS cannot carry AV1/VP9 (and HEVC-in-TS has patchy client support), so non-h264 targets require the **fMP4/CMAF segment path** (`cmafmux`/`isofmp4mux`, already a doctor row), which is also the prerequisite for HEVC pass-through to clients that only accept it in fMP4. Encoder availability rides the existing TC-1 report (a verified `hevc:`/`av1:` entry appears when the dry-run passes) and placement matches on it; the per-target verdict states codec and container. Clients keep working with zero declaration changes — the profile already lists codecs; negotiation simply stops collapsing them to one.

**HUB-16** The hub shall always prefer the cheapest sufficient path: direct play > remux > audio-only transcode > video transcode, and among sources prefer one that avoids transcoding entirely. This cost boundary is also the execution boundary: direct play, remux and audio-only transcode are hub work; video transcode is full-transcoder work.
**HUB-17** Transcoded delivery shall use an adaptive segmented protocol (HLS as baseline; LL-HLS and DASH as extensions), support seeking into not-yet-transcoded regions (session restart at seek point), and support mid-stream quality switching.
**HUB-18** The hub shall track play sessions: concurrent stream limits per user, progress checkpoints (resume state written at a fixed interval and on teardown), idle timeout and orphan cleanup, and administrator visibility into active sessions (who, what, direct/transcoded, which transcoder, throughput).
**HUB-19** Music playback shall support gapless-capable delivery and ReplayGain/loudness metadata pass-through.

### 6.5 Bundled web interface

**HUB-25** The hub shall ship with an embedded web interface — static assets compiled into the hub binary and served on the same listener as the client API — requiring no separate deployment, web server, or build step for the operator. It shall consist of two areas behind one login: an admin UI and an MVP web player.
**HUB-26** The admin UI shall cover the full admin API surface: pending enrollments with code entry and live updates (a newly submitted CSR appears without a page refresh), the satellite list with fingerprints, status, and delete (allowlist removal + cascade per SEC-6/HUB-20), library composition from announced collections with a per-library refresh action and live per-collection scan progress (HUB-35 — there is deliberately no global refresh button), enrichment configuration and the manual-match review queue (HUB-8), subtitle provider configuration, user and grant management, and an active-sessions dashboard (who, what, direct/remux/transcode, which transcoder, throughput per HUB-18).
**HUB-27** The MVP web player shall support: login; library browse and search; item detail with technical stream info and the negotiation verdict; video playback (direct, remuxed, and transcoded HLS) with seek, resume from watch state, audio-track and subtitle selection including the user-initiated subtitle search/download flow (HUB-24); and music playback with queue and album playback. The player shall derive and submit an honest capability profile from the browser's actual decode capabilities rather than a hardcoded one.
**HUB-28** The web interface shall be a pure client of the versioned public API (HUB-11/12) with no privileged private endpoints, so that third-party clients can achieve full feature parity. It shall target current evergreen browsers; broader compatibility is a non-goal for the MVP.

### 6.6 Anime

Anime is a differentiating pillar, not a skin over `series`: its metadata ecosystem (AniDB, AniList, MyAnimeList, Kitsu) is far more precise than TheTVDB/TMDB for this content, and its file conventions demand their own handling.

**HUB-29** Anime libraries shall use anime-native metadata providers behind the same provider trait: AniDB and AniList as first implementations (MyAnimeList/Kitsu as candidates), with cross-service ID mapping (including to TheTVDB/TMDB via the community anime-lists mapping) so artwork or descriptions can fall back to western providers where the anime services are sparse.
**HUB-30** Anime filename parsing shall understand fansub/release conventions: `[ReleaseGroup]`-prefixed names, absolute episode numbering as the norm, version tags (`v2`), CRC32 suffixes, batch markers, and specials/OVA/ONA/movie designations. Where ED2K hashes are available (MH-9), the hub shall use AniDB exact-file identification — hash → precise episode, release group, and version — as the highest-confidence match, above all name-based heuristics.

*Amended 2026-08-06: cross-aid re-binding is declined, and what remains
of it is narrowed to breaking collisions.* The original reading — a file
whose hash names a different AniDB entry than its show should move to
that entry's numbering — was measured against the library before being
built, and it is wrong for the common case. Of 873 hashed anime files,
217 disagree with their show's aid and **213 of those are Pokémon**,
where AniDB splits one televised series into an entry per season (aids
230, 1041, 11585) while the files are laid out, numbered and titled by
season on disk. Those files are already in the right place: moving
`Pokemon 06x01` to episode 1 of another entry would break a correct
slot to satisfy a keyspace kahawai does not present (HUB-31 makes the
numbering a per-user projection, not AniDB's to decide). A differing aid
is therefore not evidence of a misplacement.

What the hash is still owed is narrower and demonstrably real: when
SEVERAL files are bound to ONE episode slot and their hashes name
DIFFERENT AniDB episode ids, they are different episodes and shall be
split apart, taking their numbering from the hash. Several sources on
one slot is otherwise legitimate — two copies of the same episode share
an eid — so the eid, not the count, is the test. Megazone 23 is the
worked case: `pt.03-a` and `pt.03-b` both landed on S00E023, an episode
number lifted out of the *title*, while their hashes name eids 39483 and
39484 (episodes 1 and 2 of aid 3545). A number taken from a title shall
never outrank a hash that names the episode.
**HUB-30a** Hashes are canonical identity. When an ED2K hash arrives after an item has already been matched by name, the hub shall re-verify the existing match against the hash-derived identity and, on disagreement, the hash wins — overriding even a manual match, because the hash states what the file *is*. Absent such disagreement, an existing manual match is never re-decided: anime-service IDs attach to a manually matched item only through reverse ID mapping (anime-lists), never by re-running identification.
**HUB-31** The hub shall model anime structure natively — AniDB-style per-series entries with absolute numbering, plus the relations graph (sequel, prequel, side story, alternative version) — and offer per-library presentation as either native structure or TVDB-style seasons via the ID mapping. The relations graph shall be exposed to clients as a suggested watch order on the item detail.
**HUB-32** ASS/SSA subtitles shall be first-class: styling and typesetting preserved (never silently flattened to SRT), font attachments — declared at scan (MH-4), extracted on demand by the hub and cached — served alongside the subtitle stream, client-side ASS rendering supported where the client declares the capability (the bundled web player shall, per HUB-27), and burn-in via the transcoder — with the correct fonts supplied to it — as the fidelity fallback for clients that cannot.
**HUB-32a** For clients without ASS rendering, the fallback shall be a policy choice between **burn-in** (full fidelity, but requires a video encode and is memory-bandwidth heavy on low-power hardware even when the encode itself is hardware-accelerated) and **flattening** (dialogue extracted to a plain text format such as WebVTT — typesetting, signs, and karaoke are lost, but no video encode is required for the subtitles). The policy shall be configurable as a server default with per-library and per-user override, and the negotiation verdict shall state which was applied and why. When flattening is selected and video would otherwise have been encoded *only* for burn-in, the plan shall degrade to remux or direct play with the flattened text track — playable with no transcoder at all (AR-10). "Never silently flattened" stands: flattening happens only under this explicit policy or an explicit per-session user choice, and capability profiles shall carry ASS rendering as an explicit capability so negotiation can distinguish all four paths (pass-through, client render, burn-in, flatten).
**HUB-32b** For image-based subtitles (PGS, VobSub), a server-side bitmap tier shall precede burn-in in the policy order: the hub decodes the subtitle stream into timed bitmap display sets and streams them to clients that declare a graphics-overlay (compositing) capability, which render them on an overlay — full visual fidelity with zero video processing. Burn-in is applied only for clients that cannot composite an overlay. Capability profiles shall carry the graphics-overlay capability explicitly.
**HUB-32c** The hub shall additionally support **OCR of image-based subtitles** into text tracks (Tesseract via the `leptess` crate — *amended 2026-07-30: `subtile-ocr` dropped; its value is parsing `.idx/.sub` files the hub already decodes to bitmaps, and leptess is MIT where subtile-ocr is GPL-3.0*), serving two cases: (a) clients that cannot composite an overlay, where OCR-derived text is preferred over burn-in when available and enabled; and (b) low-bandwidth or high-latency links, where a text track is selectable per session by the user and remembered as a per-user preference, even for overlay-capable clients (a few KB versus a bitmap tile stream). An automatic bandwidth-threshold selection is deliberately deferred until the hub measures client bandwidth — machinery shared with the quality ladder — rather than shipping as a one-off heuristic. The full image-subtitle preference order is therefore: bitmap streaming → OCR text → burn-in, policy-adjustable per the HUB-32a mechanism. OCR support shall be an **optional-but-recommended compile-time feature, enabled by default**; at runtime it further depends on the Tesseract library and per-language trained models, and its absence (feature off, library missing, or language model missing) shall degrade gracefully — the tier is skipped in negotiation and the `doctor` command reports exactly what is missing per OPS-3. OCR results shall be cached per stream and language, stored and served like other text tracks but marked as OCR-derived (imperfect by nature, user-visible as such, reviewable and deletable), with the Tesseract language model selected from the subtitle track's language tag. *Mechanics amendment (2026-07-31, subtitle unification): every subtitle track — embedded, sidecar, downloaded, OCR — is a first-class hub row in one keyspace (`subtitle_tracks`, synced at scan); a client capability adjusts a track's computed **delivery** (`text`/`ass`/`overlay`/`burn`/`none`), never its existence in the API; the explicit per-session tier choice of HUB-32a/c is expressed as track selection (an image track picked by id forces its burn-in, overriding both the overlay preference and the OCR-spares-burn rule); OCR lineage is the row-level `derived_from` link, per source, replacing name parsing; every track has exactly one direct owner, so physical streams and their reproducible OCR/raster derivatives reference the stable source while downloaded/manual tracks reference the item, and derivatives inherit their parent's owner; and the per-item track memory of HUB-33 extends to exact track ids, which is what lets a specific downloaded or OCR row be remembered for a movie.*
**HUB-32d** *(deferred)* The hub shall be able to RASTERISE an ASS/SSA track server-side into the timed bitmap track HUB-32b already defines, and offer it to clients declaring the graphics-overlay capability. libass renders to positioned RGBA bitmaps with timing, which is that shape exactly, so the delivery path and the client-side compositing already exist. It dominates both existing fallbacks where it applies: unlike burn-in it needs no video encode, so direct play survives and no transcoder is involved; unlike flattening it keeps typesetting, signs and karaoke. Its place in the order is therefore client-native → rasterised overlay → flatten → burn.

Two things make it deferred rather than next. ASS is vector and renders at whatever size is asked, so unlike PGS's fixed authoring canvas the rasterisation is a function of display size — either rendered at the coded size and scaled by the client (uniformly by width, per HUB-32b), or re-rendered per size with the cache multiplying accordingly. And it inverts HUB-32c: OCR turns bitmaps into text because text is orders of magnitude lighter on a constrained link, where this turns text into bitmaps, so it wants the same user-chosen, per-user-remembered treatment rather than being automatic. The client that would benefit — one that composites bitmaps but cannot run libass — does not exist in this deployment yet, since the web player carries JASSUB.

**HUB-33** Anime libraries shall support dual-audio conventions: default audio selection by user preference (original + subtitles vs dub), remembered per user per library.
**HUB-34** Embedded subtitle streams and font attachments shall be retrievable without transferring or reprocessing the whole file, via an efficiency ladder tried in order: (1) already-cached data or sidecar files; (2) a tap on a live playback session's pipeline — the session is already demuxing the file, so subtitle packets are captured from it at sub-second latency at any playback position; (3) targeted extraction by the mediahost, as efficiently as the file permits (index-driven sparse reads where the container provides an index, header-walk seeking otherwise, sequential read as the floor); (4) a hub read lease with hub-side demux as the last resort. Results are cached so the ladder runs at most once per stream.
**HUB-36** Placement shall weigh **pace**, not only fitness (AR-13 rule 3; extends TC-2). A box that satisfies every codec and filter requirement may still be the wrong home for a given job: measured in this fleet, the same 2160p HDR work runs at roughly 0.65× realtime on one transcoder and several times realtime on another, and the difference is invisible to a capability inventory that reports only what elements exist and whether they are hardware-accelerated. The hub shall therefore hold a per-box throughput estimate per class of work (resolution × decode codec × filter chain), derive it from the sessions it already runs — transcoders report a realtime multiple per TC-4 — and prefer a box that can sustain realtime for the job in hand over one that merely has the right elements. A job with no box that can sustain it is still placed, on the fastest candidate, with the session verdict stating the expected shortfall rather than letting a viewer discover it as stalling.
**HUB-35** Refresh (rescan) control shall be granular, with no global "refresh everything" action anywhere in the interface. The unit of refresh presented to administrators is the **library**: refreshing a library dispatches collection-scoped scan requests (MH-2) to each collection composing it, on whichever mediahosts those collections live, with progress reported per collection and aggregated per library. A per-**collection** refresh shall additionally exist at the API level, and shall surface as an action in any present or future UI that enumerates individual collections. Refresh requests for a collection already being scanned coalesce into the running scan rather than queueing a duplicate.

## 7. Transcoder requirements

**TC-1** On registration, a transcoder shall report its capabilities: available GStreamer encoders/decoders, hardware acceleration (VA-API, NVENC/NVDEC, V4L2, QSV, VideoToolbox), max concurrent sessions, and supported filters (scaling, tone mapping, deinterlacing, subtitle burn-in, audio downmix/resample). *Amended 2026-07-29 by AR-13:* each reported item must be dry-run-verified and must decide something. A filter that every build performs, because it ships inside the binary, is not reported — the protocol version already gates it — and a filter whose viability depends on throughput is reported as a rate, not as a boolean (the same GL tone-map segment runs at 1.7× realtime at 1080p and 0.65× at 2160p on one box in this fleet, and a boolean cannot say so).
**TC-2** The hub shall schedule sessions onto transcoders using reported capabilities and live load, preferring hardware-accelerated paths that satisfy the negotiated output, and shall never schedule a job a transcoder cannot perform.
**TC-3** A transcode session shall be fully specified by the hub (input source reference, stream selection, per-stream decision: copy/encode with codec+parameters, filters, segment format and duration, start offset) — the transcoder makes no policy decisions.
**TC-4** The transcoder shall build GStreamer pipelines dynamically from the session spec, stream segments and playlists back as they are produced, honor seek (restart at offset) and quality-change commands, and report progress, throughput (realtime multiple), and errors.
**TC-5** Sessions shall be cancellable with prompt resource release; a configurable transcode-ahead window shall bound how far past the play head a session runs.
**TC-6** The transcoder shall enforce resource ceilings (CPU shares, GPU session count, scratch-disk quota with eviction of stale segments) and shall degrade predictably to software encoding when hardware acceleration fails at runtime. **Amended 2026-08-08** after auditing what a box can actually enforce; two of the three named ceilings are struck. **Eviction of stale segments** is refused, for the reason OPS-6 refuses hub-side eviction: a produced segment is not stale. A player seeks back into it without restarting the pipeline, so deleting one costs a seek-restart at exactly the moment somebody is scrubbing. Nor is it reachable while players can seek at all: in gst-plugins-rs `hlsbasesink`, tracking a segment for deletion, deleting it, and trimming it from the playlist are all gated on the playlist carrying *no* type, and `EXT-X-PLAYLIST-TYPE:EVENT` is what makes seeking within produced segments work. What a run costs is bounded by its own length and reclaimed whole at teardown — measured mid-film on the reference box: 1.50 MB per second of content for a copy of a 10.2 Mbit/s source (5.4 GB per content-hour), 0.82 MB/s for an H.264 encode of a 2.7 Mbit/s HEVC source (3.0 GB per content-hour), so a two-hour session costs 6–11 GB against a `max_sessions` of 2. **GPU session count** is struck as undiscoverable: NVML reports NVENC sessions on NVIDIA alone, VA-API and VideoToolbox expose nothing, and two of the three boxes in this fleet could never report one. It needs no reporting either — a driver at its limit refuses the encoder, and since each session's pipeline is a fresh process that dry-runs its preference list (TC-1), that refusal already degrades that session to software, which is this requirement's last clause. The enforced ceilings are therefore `max_sessions` and CPU shares (`[transcoder] worker_nice`, `worker_threads`, applied by each pipeline worker to itself). cgroup CPU weight belongs to whatever supervises the process and is documented rather than enforced.
**TC-7** *(Optional, v1.x)* Offline pre-transcode: administrators may queue background conversion of items into a chosen profile stored as an additional source.

## 8. Non-functional requirements

**NFR-1 Performance.** Direct-play start ≤ 2 s and transcoded start ≤ 6 s on reference hardware (4-core x86 with VA-API, local disk, LAN client); browse responses ≤ 200 ms at 50k items; a hub shall handle ≥ 100 concurrent direct-play sessions on reference hardware, transcode concurrency bounded only by transcoder resources.
**NFR-2 Scale.** Support ≥ 250k files across all collections, ≥ 10 mediahosts, ≥ 5 transcoders per hub without architectural change.

*Amendment (owner, 2026-08-02): what the mediahost count means.* Ten real mediahosts cannot be stood up here, and ten processes on one box prove nothing about ten disks. So the target is the claim the phrase "without architectural change" actually makes, which is entirely hub-side: the hub shall hold ten simultaneous mediahost links — ten enrolled identities in the allowlist, ten control streams with heartbeats, ten announced collections reconciling independently, and leases and sessions routed per module — with no per-module state that degrades or caps as that number grows. Per-host I/O and scan load at ten are explicitly NOT claimed, and will be measured when a deployment actually has ten.
**NFR-3 Reliability.** No data loss of user state on crash (durable writes for watch state); media files opened read-only always; clean recovery of all module connections after hub restart without rescan.
**NFR-4 Security.** All inter-module links use mutual TLS under the hub's internal CA per §4.3; client API over TLS (native or via reverse proxy); path traversal impossible by construction (mediahosts resolve only IDs, never client-supplied paths); secrets and private keys never logged.
**NFR-5 Portability.** Linux x86_64 and aarch64 as tier-1 targets (NAS-class hardware included); macOS and Windows tier-2 for the all-in-one binary; distribution as static-ish binaries with bundled or clearly-declared GStreamer plugin dependencies, plus container images per module and all-in-one.
**NFR-6 Operability.** Structured logging, Prometheus-compatible metrics, health endpoints per module, single-file TOML configuration with environment-variable overrides, and online reload for non-structural settings.
**NFR-7 Compatibility.** The client API is versioned; breaking changes only in a new major API version, with at least one prior version served concurrently during a deprecation window.
**NFR-8 Licensing.** Codec support is delegated to the system/bundled GStreamer plugin sets; builds shall make the plugin tier (base/good/bad/ugly) explicit so distributors can make patent/licensing choices deliberately. Dependency licenses shall be tracked per cargo feature. **Resolved:** Kahawai itself is licensed **MIT**. *Amended 2026-07-30:* the OCR feature links `leptess` (MIT) and Tesseract/Leptonica (Apache-2.0/BSD-style) — `subtile-ocr` (GPL-3.0) is not used, so no copyleft consequence attaches to any build. `--no-default-features` remains available to drop the Tesseract linkage entirely for minimal deployments.

## 9. Operational readiness

Gaps identified in review that would block a real first release despite not appearing in the feature surface:

**OPS-1 First-run bootstrap.** On first start with an empty database, the hub shall enter setup mode: the web UI presents a one-time flow to create the initial admin account (and nothing else is reachable until it completes); a printed one-time setup token gates the flow so a race on a freshly exposed port can't claim the instance. A CLI password-reset command (`kahawai hub reset-password <user>`) shall exist, since a self-hosted system has no email escape hatch.
**OPS-2 Login hardening.** The client API shall throttle authentication attempts (per account and per source address, with exponential backoff) and log failures; this is the front door of a system people expose to the internet.
**OPS-3 Environment self-check.** Every module shall provide a `doctor` command and run the same checks at startup: required GStreamer version and plugin inventory against the feature matrix (naming exactly which capability each missing plugin costs, e.g. "no `libde265`/`vah265` → HEVC sources will always transcode-fail"), OCR availability when the feature is compiled in (Tesseract library presence and per-language trained models, e.g. "no `jpn` model → OCR tier unavailable for Japanese image subtitles"), hardware-acceleration device access, filesystem permissions on configured directories, and clock sanity. Missing optional capabilities degrade with a logged warning; missing essentials fail fast with actionable output.
**OPS-4 Clock skew tolerance.** Satellites on RTC-less hardware (Raspberry Pi class NAS boxes) boot with wrong clocks and would fail certificate validation. Certificate validity checks shall tolerate bounded skew (leaf `notBefore` backdated at issuance; verifier allows a small grace window), and a satellite whose clock is out of tolerance shall log a specific, self-diagnosing error rather than a bare TLS failure.
**OPS-5 Backup and restore.** The hub shall provide an online backup command producing a consistent snapshot of everything needed to rebuild it: database, PKI material, downloaded subtitles, and configuration (image and provider caches are excluded as re-derivable). Restore onto a fresh install shall reconnect existing satellites without re-enrollment, since the CA and satellite records are part of the snapshot.
**OPS-6 Disk growth bounds.** All hub-side caches and stores shall be quota-bounded with defined eviction: image cache and provider cache (LRU under a configured cap), transcoder scratch (already TC-6). The user-acquired subtitle store is deliberately not evicted, but its size shall be reported. Physical OCR/raster derivatives are source-owned caches and are evicted when their source or parent stream disappears. **Amended 2026-07-26** after auditing what is actually cached: no LRU cap is implemented, because nothing the hub keeps is eligible. Each cache is expensive on at least one of two axes — cost to rebuild (a subtitle extraction re-demuxes a whole source file over a byte-plane lease; a downloaded subtitle spends a rate-limited provider entitlement) or latency at point of use (artwork is cheap to refetch but wanted instantly during a grid scroll, so a miss is a visible stall). Disk is not the scarce resource; provider entitlements, mediahost I/O and interaction latency are. A cap for a genuinely small-disk deployment belongs in an admin-triggered purge that states its cost, not a silent janitor. The single deletion that exists is unreachability, not quota: resized artwork whose size has left the code's list, or whose original is gone, is dropped at startup (§10).
**OPS-7 Upgrade compatibility.** Protocol compatibility shall be governed by **major version**: a hub and a satellite interoperate if and only if they share the same major protocol version, regardless of minor version and in either direction (older-minor satellite against newer-minor hub, and vice versa). Minor versions may therefore only make strictly additive changes — new optional messages or fields that the other side can ignore. Breaking changes require a major bump, and modules shall refuse to run across differing majors with a clear message naming both versions and the required action. Within a major, rolling upgrades are supported in any order with mixed versions functional indefinitely; only a major bump imposes an upgrade order, shipped with explicit migration notes. The all-in-one binary is exempt (always self-consistent).

*Amendment 2026-08-13 — flatten without catalogue loss.* Before 1.0.0, accumulated additive wire shapes shall be folded into a clean major and satellites upgraded together. A wire-major break is not permission to discard catalogue identity: it shall not force an authoritative collection rescan, reset scan generations, clear source bindings, rematch media, repeat provider work, or lose user state. Facts absent from records written by an older scanner shall be filled by bounded, fact-specific worklists whose writes cannot reconcile the catalogue or alter identity. Protocol 3 applies this rule to exact-root identity: protocol-2 peers are refused, while migration and targeted content-identity checks adopt existing source rows losslessly.
**OPS-8 Reverse-proxy operation.** Since most deployments will sit behind a reverse proxy, the hub shall document and support: WebSocket upgrade for `/api/v1/events`, `X-Forwarded-For`/`X-Forwarded-Proto` trust configuration (needed for OPS-2 throttling to see real client addresses), and a configurable CORS allowlist for third-party web clients (HUB-28 parity). Deployment documentation shall note that the web player's ASS renderer requires WASM assets to be served with the `application/wasm` MIME type by any server or CDN fronting the interface.

**OPS-9 Decoder rank calibration, measured and remediable.** The `doctor` command shall detect decoders that GStreamer ranks above a better alternative on this box, and shall be able to write the corrections itself.

*Detection.* Two classes, and presence checks see neither. (a) **Pathologically slow hardware decode**: on Gemini Lake, `vah265dec` decodes at ~6 fps where `avdec_h265` does ~121 — the element is present, advertises the codec, and works, so only a measurement distinguishes it. The check shall time each hardware decoder that outranks software against the same reference clip the TC-1 benchmarks use (`kahawai-media/src/bench.rs`, already built for encoders) and warn when the hardware path is slower than software, naming both figures. (b) **Decoders that see less of the stream than the alternative**, of which the existing DTS row is one instance: `dtsdec` (libdca) decodes only the lossy DTS core, so a DTS-HD MA 7.1 track decodes — and, when a scan autoplugs it, is *recorded* — as 5.1 (measured 2026-08-01: 8 channels via `avdec_dca`, 6 via `dtsdec`; the library held 312 DTS files at 6 channels and none at 8). This class is a fixed known-bad list, not a measurement.

*Remediation.* `doctor --fix` shall write the demotions this box needs into its configuration file — `[transcoder] demote_decoders` for what playback autoplugs and `[mediahost] demote_decoders` for what discovery does, since the two are separate lists precisely because a decoder can be right for one job and wrong for the other (`dtsdec` belongs in both: it decodes the wrong thing *and* files the wrong thing). The write shall be idempotent, shall preserve existing entries, comments and formatting, shall state every change it makes and why, and shall never remove a demotion a human put there. Since a demotion is per-box calibration, `--fix` shall act only on the box it runs on and only on decoders it has either measured or holds on the known-bad list.

*Why this is a requirement and not a runbook.* The DTS rank check already existed and already warned, in exactly the words that describe the bug; it warned on a box nobody was reading the output of, and the library silently accumulated 312 wrong channel counts. A check whose remedy is a hand-edited TOML on each satellite is a check that will be ignored.

**OPS-9a** The decoder timing of OPS-9 shall cover every codec for which this deployment can autoplug a hardware decoder, not only those with a checked-in reference bitstream.

**OPS-10 Session diagnostics as one downloadable bundle.** A session's diagnostics shall be retrievable from the interface as a single text bundle, by an administrator, without shell access to any machine.

*Why a requirement.* Diagnosing one hung session took four sources stitched together by hand — the hub log, the run directory over ssh, a segment pulled with scp and walked for NAL types, and `viewer.pos` against the segment count. A user reporting "it hangs" can supply none of that, and the evidence is deleted with the run directory the moment the session is torn down.

*Capture.* **One store, whatever went wrong.** Splitting crashes from ordinary sessions would require knowing which kind of failure is being chased before anything is known about it, which is backwards. A bundle shall be assembled when a session ENDS, not only when it fails, because a hang never fails — and it shall be assembled BEFORE the run directory is removed, which on the satellite happens synchronously during teardown. It shall additionally be assembled when a session FAILS — including a failure so early that the session never began, which is why the session identifier is minted before any work that can fail — and be obtainable on demand while a session is live. Retention is bounded like the crash store (newest N, byte-capped per bundle); a crash loop must not fill the disk it is reported on.

*Content.* The bundle carries what the two sides each know and the other cannot: from the hub, structured session state — item, user, mode, plan, verdict, placed box, work class, sink — because the hub cannot read its own log (it writes to stdout, redirected by whatever launched it); from the executing box, the worker log, the session facts, playlist and position files, and a one-line verdict on whether the FIRST segment is independently decodable, which is the single fact that distinguishes "the pipeline is fine and the player is stuck" from everything else.

*Reach.* An administrator shall be able to take the bundle from the admin session list, from the player while the problem is on screen, and from an item's detail page after the fact — the last returning the newest session for that item whoever played it, since the purpose is debugging somebody else's report.

## 10. Acceptance criteria (v1)

1. All-in-one binary on a single machine: scan a mixed library (H.264/HEVC/AV1 video, FLAC/MP3/AAC audio, PGS+SRT subtitles), enrich from TheTVDB/TMDB/MusicBrainz, then browse, search, and play from the bundled web player, with library composition and match review done in the bundled admin UI. Additionally: an anime collection with fansub-convention filenames matches correctly via AniDB/AniList (hash-exact where ED2K hashes have been computed), presents a watch order, and plays with ASS subtitles rendered client-side in the web player with correct fonts.
2. Direct play of a compatible file with seek via byte ranges; remux of a compatible-codec MKV to fMP4/HLS without re-encoding, performed by the hub with **no transcoder attached**; HEVC→H.264 hardware transcode with PGS burn-in and AC-3→AAC stereo downmix, with seek and quality switch.
3. Modular deployment across three machines (hub / mediahost / transcoder) passes the same client-visible test suite as the all-in-one deployment.
4. Kill the mediahost mid-playback: session errors surface cleanly, library shows unavailable, reconnection restores availability without rescan. Kill the transcoder mid-playback with a second transcoder attached: session resumes on the second within 10 s.
5. Enrollment, deletion, and restore: a fresh satellite prints its code, is approved by entering the code on the hub, and connects over mTLS; entering a wrong code rejects the enrollment; a certificate validly signed by the hub CA but absent from the allowlist is refused at the TLS layer. Deleting an enrolled mediahost removes its fingerprint from the allowlist, drops its connection within 5 s, refuses reconnection, and removes its collections from all libraries; re-enrolling the machine and rescanning restores its items with prior manual matches and watch state intact.
